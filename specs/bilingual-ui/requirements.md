# 需求规格：支持中英双语 UI，并允许用户在右上角切换语言

## 背景

当前项目的 UI 文案基本为英文硬编码，且根布局 `app/layout.tsx` 中固定使用 `lang="en"`。虽然项目可以显示中文内容消息，但并不具备“中文 / 英文界面切换”的产品能力。

新需求要求项目支持 **中文（zh-CN）** 与 **英文（en）** 两种 UI 界面语言，并在页面 **右上角** 提供显式语言切换入口，让用户能够随时切换界面语言。

## 目标

- 为项目引入统一的 UI 国际化机制，支持 `en` 与 `zh-CN` 两种语言。
- 在用户可见的主要界面中提供位于右上角的语言切换器。
- 让用户切换语言后，当前页面的 UI 文案立即切换，并在刷新后继续保持所选语言。
- 在不改动现有聊天核心能力的前提下，为后续继续扩展更多语言保留清晰结构。

## 范围

### In Scope

- 支持 `en` 与 `zh-CN` 两种 UI 语言
- 引入统一的语言配置、词典与取词机制
- 根据当前语言渲染主要界面文案
- 在登录 / 注册页面右上角提供语言切换器
- 在聊天主界面顶部右上角提供语言切换器
- 持久化用户语言选择，使刷新后仍保持原设置
- 根据当前语言设置 `<html lang>`
- 本地化主要静态文案、按钮、占位符、提示、空状态、确认弹窗、toast、导航文本、建议问题等 UI 文案
- 按语言维护建议问题集合，允许中文与英文使用各自更自然的预置建议内容

### Out of Scope

- 自动翻译用户输入、历史消息或模型回复内容
- 为 URL 增加 `/en`、`/zh-CN` 这类语言前缀路由
- 引入除中文和英文之外的第三种语言
- 翻译 README、部署脚本、数据库内容或日志
- 改变模型供应商、模型能力和聊天业务逻辑
- 按用户账号写入数据库级语言偏好

## 假设

1. 项目在本次需求中只需要支持 `en` 与 `zh-CN` 两种语言。
2. 语言偏好可以通过 cookie 持久化，无需新增数据库字段。
3. 当前项目更偏向已登录 Web App，而不是依赖搜索引擎索引的多语言营销站点，因此无需引入 URL 级多语言路由。
4. 本次“支持双语 UI”指项目自带界面文案双语化，不包含模型输出自动跟随 UI 语言。
5. 右上角语言切换器至少需要出现在登录 / 注册页与聊天主界面，保证用户进入产品后随时可切换。

## 用户故事

### 用户故事 1
作为中文用户，我希望把界面切换为中文，这样我可以更自然地理解按钮、提示和导航文案。

### 用户故事 2
作为英文用户，我希望保留英文界面，这样我可以继续使用熟悉的默认语言。

### 用户故事 3
作为任意用户，我希望在右上角直接切换语言，而不需要修改 URL、清空缓存或重新登录。

### 用户故事 4
作为回访用户，我希望系统记住我上次选择的语言，这样我刷新页面或稍后再次访问时不需要重复设置。

## 验收标准（EARS）

### 功能需求

#### R1. 支持的语言与默认解析
1. WHEN 系统渲染页面 THEN 系统 SHALL 支持 `en` 与 `zh-CN` 两种 UI 语言。
2. IF 请求中存在合法且受支持的语言偏好 THEN 系统 SHALL 使用该语言渲染界面。
3. IF 请求中不存在已保存语言偏好 THEN 系统 SHALL 根据浏览器语言偏好在 `en` 与 `zh-CN` 中选择最匹配的语言。
4. IF 浏览器语言偏好无法匹配受支持语言 THEN 系统 SHALL 回退到英文界面。
5. IF 读取到不受支持的语言值 THEN 系统 SHALL 忽略该值并回退到有效默认语言。

#### R2. 右上角语言切换入口
6. WHEN 用户访问登录页或注册页 THEN 系统 SHALL 在页面右上角展示语言切换器。
7. WHEN 用户访问聊天主界面 THEN 系统 SHALL 在顶部右上角展示语言切换器。
8. WHEN 用户打开语言切换器 THEN 系统 SHALL 清晰展示 “English” 与 “中文” 两个可选项。
9. WHEN 当前语言已被选中 THEN 系统 SHALL 在语言切换器中明确标识当前选项。

#### R3. 切换行为与当前页面保持
10. WHEN 用户在语言切换器中选择另一种语言 THEN 系统 SHALL 切换当前页面的 UI 文案到所选语言。
11. WHEN 用户切换语言 THEN 系统 SHALL 保持用户停留在当前页面与当前路由，而 SHALL NOT 把用户跳回首页。
12. WHEN 用户从英文切换到中文或从中文切换到英文 THEN 系统 SHALL 在一次明确操作后完成切换，而不要求用户重新登录。

#### R4. 语言偏好持久化
13. WHEN 用户完成语言切换 THEN 系统 SHALL 持久化该语言偏好。
14. WHEN 用户刷新当前页面 THEN 系统 SHALL 继续使用最近一次选择的语言。
15. WHEN 用户在同一浏览器中打开新的应用页面 THEN 系统 SHALL 继续使用最近一次选择的语言。

#### R5. UI 文案本地化覆盖范围
16. WHEN 系统渲染登录 / 注册页面 THEN 标题、说明、表单标签、提交按钮、跳转链接与错误提示 SHALL 使用当前语言。
17. WHEN 系统渲染聊天主界面 THEN 欢迎语、输入框占位符、侧边栏导航、历史记录分组标签、按钮、菜单项、确认弹窗与 toast SHALL 使用当前语言。
18. WHEN 系统渲染建议问题、空状态、删除确认、可见性选择器、模型搜索占位符、消息操作 tooltip 等预置 UI 文案 THEN 这些文案 SHALL 使用当前语言。
19. WHEN 当前语言切换时 THEN 建议问题 SHALL 切换为该语言对应的预置内容集合，且 MAY 使用针对该语言单独编写的自然表达，而不要求逐字直译。
20. WHEN UI 中显示品牌名、模型供应商名或用户 / 模型生成内容 THEN 系统 SHALL NOT 强制翻译这些动态内容，除非其本身属于预置界面文案。

#### R6. 语言相关的文档与可访问性信息
21. WHEN 页面使用某种语言渲染 THEN 系统 SHALL 将根文档 `<html lang>` 设置为对应语言值。
22. WHEN 当前语言为中文 THEN 系统 SHALL 以可读、自然的中文标签展示语言名称与主要导航文案。
23. WHEN 当前语言为英文 THEN 系统 SHALL 以自然英文展示语言名称与主要导航文案。

#### R7. 降级与容错
24. IF 某个翻译 key 缺失对应语言文本 THEN 系统 SHALL 回退到英文文本，而 SHALL NOT 直接显示 `undefined`、空白或崩溃。
25. WHEN 语言切换请求失败 THEN 系统 SHALL 保持当前界面可用，并向用户提供可理解的错误反馈。
26. WHEN 系统加载本地化资源 THEN 系统 SHALL 不影响现有登录、聊天、历史记录、文档和上传等核心功能的可用性。

#### R8. 可维护性与质量要求
27. WHEN 开发者新增新的界面文案 THEN 实现结构 SHALL 支持通过统一词典机制继续扩展，而不是继续新增散落的硬编码字符串。
28. WHEN 本次功能完成 THEN 双语实现 SHALL 尽量复用现有 Next.js / React 结构，并避免为仅两种语言的 UI 场景引入过重复杂度。
29. WHEN 中文界面启用 THEN 主要界面文本 SHALL 可正常显示，且不应因字体配置导致明显不可读。
30. WHEN QA 验证双语功能 THEN 应可通过明确的手工步骤与自动化测试验证切换、持久化与关键页面文案覆盖。
31. WHEN 视口较窄或处于移动端 THEN 顶部主导航控件与右上角语言切换器 SHALL 保持可见、可操作且不互相遮挡。

## 边界情况

- 用户首次访问，没有语言 cookie，但浏览器优先语言为 `zh-CN`
- 用户首次访问，没有语言 cookie，浏览器优先语言为不受支持的其他语言
- 语言 cookie 被手动篡改为非法值
- 用户在登录页切换语言后再进入注册页
- 用户在聊天页切换语言时当前页面处于已有会话状态
- 用户在移动端打开页面，语言切换器仍需可见且可操作
- 用户切换语言后立即刷新页面
- 某个 UI key 的中文翻译暂时缺失
- 某些内容为用户生成文本、模型回复或品牌名，不应被错误翻译
- 历史记录日期分组（Today / Yesterday / Last 7 days / Last 30 days / Older）需要随语言变化
- Toast 与弹窗文案既可能来自客户端逻辑，也可能来自服务端状态映射；toast 既可能通过自定义封装触发，也可能直接通过 `sonner` 调用

## 完成定义

本规格完成时，应至少具备以下产物：

- Requirements 文档
- Design 文档
- Tasks 文档
- 一套明确的语言解析、词典管理、UI 取词、切换与持久化设计
- 可追踪到布局、顶部切换器、主要界面文案、错误处理与测试验证的任务拆分
